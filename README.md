# 企业知识库 RAG 问答 Agent

一个**零第三方依赖、可离线复现**的 RAG + Agent 参考实现：结构感知切块、BM25 与稠密向量混合检索、RRF 融合、特征重排、状态机 Agent 编排、逐条引用校验、以及一套带真实指标的离线评测。

> 为什么强调「零依赖」：目标环境没有 GPU、也装不了 torch / faiss。把每一层做成可插拔接口后，默认路径用 numpy 就能跑通全链路，接 BGE / OpenAI embedding 只需实现一个 `encode()`。这不是妥协，而是一个可以讲清楚的工程取舍。

## 目录结构

```
kb_agent/
├── kb_agent/
│   ├── text.py        # 归一化、切句、中文单字+双字分词、语料驱动分词
│   ├── chunking.py    # Markdown 结构感知切块（章节路径写入元数据）
│   ├── index.py       # BM25 + TF-IDF/SVD 稠密向量 + RRF 融合
│   ├── rerank.py      # IDF 覆盖 / 标题命中 / 稠密 / 稀疏 / 答案类型 特征重排
│   ├── generate.py    # LLM（OpenAI 兼容）可插拔 + 抽取式兜底
│   ├── agent.py       # route → retrieve → grade → rewrite → answer → verify 状态机
│   ├── evaluate.py    # 检索消融 + 端到端指标 + 阈值扫描
│   └── cli.py         # 命令行入口
├── data/docs/         # 9 篇企业制度/产品文档（约 1.1 万字）
├── data/qa/           # 48 题评测集（42 可答 / 6 不可答）
├── tests/             # 22 个单元测试
└── results/           # eval_report.md / eval_report.json / eval_details.json
```

## 快速开始

只依赖 Python 3.10+ 与 numpy：

```bash
python -m unittest discover -s tests -v     # 22 个单测
python -m kb_agent.evaluate                 # 复现评测报告
python -m kb_agent.cli "回滚平均耗时多久？"   # 单题问答
python -m kb_agent.cli "P0 故障多久响应？" --json   # 含 trace 与引用
```

接入真实 LLM（DeepSeek / OpenAI / vLLM 均可）：

```bash
set DEEPSEEK_API_KEY=sk-xxx
python -m kb_agent.cli "回滚平均耗时多久？" --llm
```

## 链路

```
问题
 └─ route        寒暄/短句分流
 └─ retrieve     kb_search 工具：BM25 + 稠密 → RRF → 特征重排 → top-6
 └─ grade        内容词覆盖率 + 未登录实体检测 → 回答 / 改写 / 拒答
 └─ rewrite      伪相关反馈：把命中最好的章节名回填 query，最多 1 次
 └─ answer       LLM 生成或抽取式兜底，强制 [n] 引用
 └─ verify       逐条引用与证据做词项覆盖校验，无有效引用则降级为拒答
```

## 评测结果

语料 9 篇文档 / 36 个 chunk；评测集 48 题（42 可答、6 不可答）。生成层为离线抽取式，因此延迟不含 LLM 调用。

### 检索消融

| 策略 | Recall@1 | Recall@5 | MRR@10 | nDCG@10 |
| --- | --- | --- | --- | --- |
| BM25 | 0.833 | 1.000 | 0.902 | 0.926 |
| 稠密（TF-IDF+SVD） | 0.881 | 1.000 | 0.925 | 0.940 |
| RRF 混合 | 0.833 | 1.000 | 0.902 | 0.926 |
| **混合 + 特征重排** | **0.905** | 1.000 | **0.944** | **0.959** |

### 端到端

| 指标 | 数值 |
| --- | --- |
| 可答问题作答率 | 95.2% |
| 引用准确率 / 召回率 | 84.5% / 86.9% |
| 不可答问题拒答率 | 83.3% |
| 延迟 P50 / P95 | 2.4 ms / 3.0 ms |

### 拒答阈值扫描（内容词覆盖率门控）

| 阈值 | 作答率 | 引用准确率 | 拒答率 |
| --- | --- | --- | --- |
| 0.35 | 100% | 84.5% | 50.0% |
| 0.50 | 100% | 84.5% | 66.7% |
| **0.52** | **95.2%** | **84.5%** | **83.3%** |
| 0.60 | 88.1% | 78.6% | 83.3% |

阈值从 0.50 提到 0.52 时，拒答率从 66.7% 升到 83.3%，只损失 4.8% 的作答率，因此选 0.52 作为工作点。

## 设计取舍（面试可讲）

1. **为什么切块要带章节路径**：引用要能落到「《发布与回滚流程》/ 回滚操作」，而不是一段无出处文本；章节标题同时是最强的重排特征。
2. **为什么 RRF 单独用反而没提升**：BM25 与 LSA 稠密向量的候选高度重叠，融合只改变排序稳定性；真正的增量来自重排层（标题命中 + IDF 覆盖），Recall@1 提升 7.2 个点。
3. **为什么不用 cross-encoder 重排**：环境装不了 torch；把重排做成特征融合后，替换成 cross-encoder 只需要改 `rerank()`，接口不变。
4. **为什么要引用校验**：生成层会编造 `[3]` 这种不存在的引用，verify 节点逐条做证据覆盖校验，校验不过就降级拒答，避免"看起来有出处"的幻觉。
5. **为什么拒答要做 OOV 检测**：检索分数对「钉钉」「IPv6」这类语料里不存在的实体依然很高，只靠相似度阈值会强行作答。

## 已知局限

- 语料只有 9 篇文档、48 题，指标方差大，不能外推到真实企业库。
- 稠密向量是 TF-IDF+SVD（LSA），不是 BGE 这类预训练 embedding；换真实 embedding 后稠密一路的 Recall@1 应显著高于 0.881。
- 默认生成是抽取式，答案 F1 只有 0.485；接 LLM 后应明显提升，但离线环境无法验证。
- 未做增量索引、权限过滤、多轮对话与流式输出。
